## PR #11: what checks out

- **The two new remotes.** `RescueBegin` and `RescueEnd` (`CatService.luau:711-793`) take one id through `Guard.id`, need a loaded profile, a live stuck cat and an unlocked area, refuse while carrying, and check range (`GrabRangeStuds + 2` from the spot anchor) at both ends. The hold is timed on the server's `os.clock()` from the `RescueBegin` arrival, with `RingLatencyGraceSeconds` (0.25 s) as the only allowance, so a scripted client gains nothing over holding E: the fastest legal rescue is still 3.75 s after its own `RescueBegin`. A short `RescueEnd` drops the lock. A `RescueEnd` after the lock lapsed is refused. The 6 s lock is cleared by a `task.delay` keyed on `lockAt`, so a newer lock is never cleared by an older timer. One lock per player is enforced by releasing any other spot the player holds. Leaving clears the player's rescue locks. `RescueBegin` has its own 1 per second bucket in `Net.luau`; `RescueEnd` sits under the default 10 per second and every path through it is a table lookup plus one fire.
- **No client data reaches the save.** `rescued` is set only from the server's carry record (`Carry.rescued`), and `ProfileSchema.migrate` keeps it only when it is exactly `true`. The 1.10x sits inside `CatStats.rating`, so income, equip best and the cat room agree.
- **gloves to net.** `ProfileSchema.migrate` carries a saved `gloves` level to `net` unless `net` was saved too, clamps it to the new def and drops unknown ids. QA's spec covers the three cases.
- **Odds.** `Catching.pickRarity` now scales by the table's total. Every odds table in `Catalog` (three lures, two areas) sums to 100, so lure odds read exactly as before and the odds the shop would show under `monetization-policy` stay true. `rescueOdds` matches data-model section 10.
- **Clock.** The phase comes from the pure `Clock.phaseAt` on the server's own clock; `PhaseEndsAt` is published on the `GetServerTimeNow()` clock, which every client shares. The generation counter stops a timer from before a debug jump. `Signal` runs each handler in `task.spawn`, so a failing night wave cannot stop the clock.
- **Night waves.** `startWave` leaves bait strays alone and keeps a mid-swing stray until its lock clears. `despawn` is idempotent, so the swing's own despawn and the wait loop cannot double free.
- **Debug hooks** assert `RunService:IsStudio()` and live in a server-only module.
- **Client.** Lighting, lamps, the Closed sign and customers are cosmetic and read the replicated `Clock` folder. The `UIController` cleanup (`task.delay(0.5)` keyed on the hold's start time) closes my PR #7 nit about the per-stray maps after a full hold. `CatchPrompt.luau` now reads `Config.RescueHoldSeconds` with no cast, which closes N17 of the review-fixes doc.

## PR #11: findings

**S20 (should-fix) A rescue lock never lapses while its holder keeps pressing.** `onRescueBegin` lets the current holder lock again (`CatService.luau:729`), and `setRescueLock` (`:743`) resets `lockAt`, which is both the hold timer and the lock age. Tapping E once every few seconds, with no script, keeps the spot locked for as long as the player likes, and everyone else gets "Someone else is rescuing it". RescueLockSeconds was meant to bound this. Impact: one player can deny one rescue spot to the whole server for a night; low stakes, but reachable by a child who wants to guard "their" cat. Fix: keep two times on the entry. `holdAt` is reset by each `RescueBegin` and used for the 4 s check. `lockedSince` is set only when the lock passes to a new player, and the holder's re-lock is refused once `os.clock() - lockedSince` passes a cap (for example `2 * RescueLockSeconds`, room for two honest tries). When the cap ends a lock, refuse that player on that spot for `RescueLockSeconds`, so someone else can step in.

**S21 (should-fix) A swing that lands after a rescue overwrites the carried cat.** `resolveGrab` (`:560-576`) calls `startCarry` without checking `carrying[player]`, and `startCarry` (`:526-528`) overwrites the record. `onGrabBegin` checks carrying, but only at the start of the swing. Rescue is a second way to start a carry, so a client can now have both open at once: `RescueBegin`, then `GrabBegin` on a stray within reach at 3.0 s, then `RescueEnd` at 3.8 s (the player now carries the rescued cat), then `GrabEnd` at 4.3 s, which rolls a perfect swing. On a catch, the rescued cat is gone from `carrying` and is never saved, and its `HeldCat` model stays welded to the character until respawn, because `attachHeldCat` only destroys the new carry's model. The honest UI shows one prompt per key, so this takes a script, and the player only hurts themselves. It is still an invariant worth keeping. Fix: in `resolveGrab`, before rolling, drop the lock and answer `GrabResult(id, false, "Check in the cat you are carrying first", true)` when `carrying[player] ~= nil`. Also make `startCarry` refuse when a carry exists, so any third capture path is covered.

**N20 (nit)** `string.format("Hold for the full %d seconds", Config.RescueHoldSeconds)` (`:775`): Luau truncates `%d`, so a tuned 3.5 would read "3 seconds". Use `%g`.

**N21 (nit)** The `GrabResult` handler in `UIController.luau:248` ignores the id. Strays and rescue spots now share the event and the card, so a late result for one target, such as a stray's 1.75 s auto-resolve, can close or hide the card of the next target, including an open rescue hold after PR #13. Compare the id with the active prompt's `StrayId` or `RescueSpotId` and drop a mismatch. The window is about one round trip wide, so this is rare.

**N22 (nit, mobile perf)** `WorldController.luau:102` listens to `Workspace.DescendantAdded` for the whole place, so every part of every wave stray, carried cat and customer runs an `IsA` check. That is cheap, but there is no reason to pay it. Listen on the `World` folder (the lamps' home) once it exists.

**N23 (nit, cosmetic)** The day tween (`WorldController.luau:95`) runs `ClockTime` from 21.5 back down to 14, so the sun sets in reverse at dawn. Tween to 38 (Lighting wraps `ClockTime` into 0 to 24) or set the day instantly.

Not a finding: `RescueBegin` on a spot whose cat was just rescued returns without a `GrabResult`. The prompt disappears with the model, which closes the card, and a late `RescueEnd` answers "Someone else got there first".

## PR #13: rescue rejection in the UI

Sound. `UI.catch.fail` now closes an open hold (`holdOpen = false`), so a rejected `GrabBegin` or `RescueBegin` sends nothing more. The deferred HoldEnded and `finishRescue` already return on a closed hold, and the swing branch of `PromptTriggered` now does too. `CatchPrompt.fail` stops and hides the rescue bar and uses rescue wording. `startRing` and `startRescue` bump the fail token, so a pending 1.4 s retry reset cannot wipe a new hold. Without this PR, PR #11's rejections would leave the bar filling and send a `RescueEnd` the server can only refuse. N21 above is the remaining edge: the fail is not matched to its target.
