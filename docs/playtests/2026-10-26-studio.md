## Bugs

### [major] Carry state never cleared after check-in  (found by: rescue and catch runs on fa20123) FIXED in PR #50
Owner: engineer
Repro: 1. Catch or rescue any cat. 2. Walk to your door; the cat checks in (placed, WalkSpeed back to 16).
3. `RequestSync`.
Expected: `carrying = nil`, the carry banner and the door marker hide, the next tutorial hint shows.
Actual: `ProfileSync.carrying` stayed the last catId. `CatService.endCarry` cleared its own map but never called
`CafeService.setCarrying(player, nil)`. The banner stayed on screen and `refreshTutorial` returned early forever.
Evidence: `evidence/2026-10-26/studio-carry-banner-stuck-fa20123.jpg` (before), `studio-carry-banner-fixed-921e564.jpg`
(after: banner gone, tutorial hint back). Verified on 921e564: fresh sync `carrying = nil`, banner hidden.

### [major, tooling] Debug hooks unusable from the command bar and MCP execute_luau  FIXED in PR #50
Owner: engineer
Repro: while playing, `require(game.ServerScriptService.Server.Services.Debug).snapshot()` from the command bar or
`execute_luau`.
Expected: the game's state.
Actual: those contexts get a fresh copy of the modules: ProfileStore prints its mock warning a second time and every
call errors `profile not loaded for <name>`; `setPhase` would drive an unstarted ClockService. A second gotcha: timers a
Debug call starts belong to the calling script, so destroying that script stopped the day and night clock for good.
Verified on 921e564: `game.ServerStorage.PurrPotDebug:Invoke("setCoins", nil, 5000)`, `("snapshot")` and `("clock")`
work from `execute_luau` on the server.

## How this run was driven
Studio MCP (`StudioMCP.exe --stdio`) from a small Python client. Calls that need the game's own module state were
run by injecting a Script (server) or LocalScript (client) that requires the modules, then reading its result
attribute; since PR #50 the `PurrPotDebug` bridge covers the Debug calls directly. Clients and Servers opens one Studio
process per player and each is reachable as its own MCP instance. Catch presses for the success path were scripted on
the circle targets (the data-model's accepted exploit path), so they test the server, not human timing.
